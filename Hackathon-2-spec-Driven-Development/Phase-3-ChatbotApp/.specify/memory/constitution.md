# Todo Evolution Constitution

## Project Name

hackathon-todo

## Vision

Build a multi-phase Todo application that evolves from console → full-stack web → AI-powered chatbot. All development follows strict spec-driven principles using Claude Code and Spec-Kit Plus. No manual coding allowed.

## Core Principles (Non-Negotiable – Zero Tolerance)

### I. Zero Manual Coding Allowed

Every line of code (Python, TypeScript, YAML, Docker, Helm, etc.) MUST be generated by Claude Code after refining specifications. Manual edits are permitted ONLY for fixing syntax errors and MUST be documented in commit messages with the associated Task ID. Judges will review Claude Code prompts, iterations, and chat history to verify compliance.

**Rationale**: This principle ensures the hackathon's spec-driven development mandate is upheld and demonstrates that AI-assisted development can produce production-quality systems without manual intervention.

### II. Spec-Driven Development is the Single Source of Truth

All features, architecture, APIs, database schema, UI components, and deployment configurations MUST originate from the `/specs/` folder. Every implementation MUST trace back through: Task ID → Plan → Specification → Constitution. All prompts MUST use `@specs/path/to/file.md` referencing to maintain traceability.

Workflow: specify → plan → tasks → Claude Code generation.

**Rationale**: Traceability from implementation to specification ensures auditability, consistency, and adherence to the hackathon's judging criteria.

### III. Reusable Intelligence Mandatory (+200 Bonus Target)

The project MUST actively create and use:
- At least 10 Agent Skills in `.claude/skills/`
- At least 10 Subagents in `.claude/agents/`

Delegation pattern required: Orchestrator → Specialized Agents → Skills. Skills and subagents MUST be reused across phases. All prompts and commits MUST demonstrate clear delegation patterns.

New intelligence components MUST be created for:
- MCP tool building
- Cohere API integration
- Conversation persistence
- Agent orchestration

**Rationale**: Reusable intelligence components demonstrate mastery of agentic development patterns and maximize the +200 bonus points allocation.

### IV. Phase III – AI Todo Chatbot Integration

Phase III extends the Phase II FastAPI backend (Neon DB, SQLModel, Better Auth JWT) with AI chatbot capabilities. Requirements:

- Extend existing FastAPI backend without breaking Phase II functionality
- Add stateless `/api/{user_id}/chat` endpoint
- Build MCP server using Official MCP SDK inside backend
- Expose 5 stateless tools: `add_task`, `list_tasks`, `complete_task`, `delete_task`, `update_task`
- Persist conversation state in Neon DB (Conversation + Message models)
- Use OpenAI Agents SDK for agent logic
- Replace OpenAI API with Cohere API key for ALL LLM calls (both agent + any other reasoning)

**Rationale**: Phase III demonstrates AI-native development while preserving the solid foundation built in Phase II.

### V. Environment Variables (Mandatory)

All secrets MUST be loaded from `.env` file. The following environment variables are REQUIRED:

- `BETTER_AUTH_SECRET`: JWT authentication secret
- `BETTER_AUTH_URL`: Better Auth service URL
- `DATABASE_URL`: Neon PostgreSQL connection string
- `COHERE_API_KEY`: Used for ALL LLM reasoning (OpenAI Agents SDK + any other calls)
- `NEXT_PUBLIC_OPENAI_DOMAIN_KEY`: ChatKit frontend domain key

Never hardcode secrets. All LLM calls MUST use the Cohere API key, not OpenAI.

**Rationale**: Proper secrets management is fundamental to security and enables deployment across environments without code changes.

### VI. Security & Authentication

The following standards are NON-NEGOTIABLE:
- Reuse Phase II JWT (Better Auth) for all endpoints including chat
- Strict user isolation – users can only see their own tasks
- Input validation and sanitization MUST be implemented on ALL endpoints
- Response formatting MUST be consistent across the entire API surface
- Integration testing MUST follow every major feature implementation

**Rationale**: Security and quality are foundational to production-ready systems and critical for hackathon judging.

### VII. Stateless Design

Chat endpoint and MCP tools MUST be stateless. All state MUST be persisted in Neon DB.

- No in-memory session storage
- Each request MUST be self-contained with user context from JWT
- Conversation history retrieved from database per request
- MCP tools operate on database directly, no cached state

**Rationale**: Stateless design enables horizontal scaling, simplifies testing, and ensures reliability across restarts.

### VIII. Monorepo & Structure Compliance

The project MUST adhere to:
- Monorepo structure exactly as specified in hackathon guidelines
- Spec-Kit Plus configuration is MANDATORY
- Multiple layered `CLAUDE.md` files for context management
- Organized `/specs` folder with subdirectories: `features/`, `api/`, `database/`, `ui/`

**Rationale**: Consistent structure enables efficient navigation, proper context injection, and demonstrates organizational excellence.

### IX. Bonus Features Targeted (+400 Possible)

The project targets the following bonus point allocations:
- **Reusable Intelligence** via subagents and skills: +200 points
- **Multi-language Support** (Urdu in chatbot): +100 points

Implementation of bonus features MUST NOT compromise core functionality or principle compliance.

**Rationale**: Strategic bonus targeting maximizes competitive positioning while maintaining core quality.

### X. Deliverables Excellence & Violation Hierarchy

All deliverables MUST meet these standards:
- Public GitHub repository with clean, logical commit history
- Comprehensive README with setup instructions and demo guidance
- 90-second demo videos clearly showing spec → implementation flow
- Clear commit messages including Task IDs and feature references
- Reference specs in every implementation
- Clean commits with Task IDs
- Maintain separation: frontend, backend, MCP, agent logic

When conflicts arise, this precedence MUST be followed:
1. **Constitution** (this document – highest authority)
2. **Specification** (`/specs/` files)
3. **Implementation Plan** (`plan.md`)
4. **Task Definitions** (`tasks.md`)

Any agent, subagent, or skill detecting a violation MUST stop execution and request clarification before proceeding.

**Rationale**: Clear hierarchy prevents cascading errors and ensures constitutional principles are never overridden. Deliverable quality directly impacts judging scores.

## Violation Rules

Any deviation from the following MUST be corrected immediately:
- Manual code (not generated by Claude Code)
- Breaking Phase II backend functionality
- Not using Cohere API key for LLM reasoning
- Stateful design patterns in chat or MCP tools
- Hardcoded secrets

If in doubt, stop and request clarification.

## Governance

### Amendment Process

1. Amendments MUST be documented with rationale
2. Amendments require explicit approval and migration plan
3. All dependent artifacts (specs, plans, tasks) MUST be updated to reflect amendments
4. Version number MUST be incremented according to semantic versioning

### Versioning Policy

- **MAJOR**: Backward incompatible changes to principles or removal of core constraints
- **MINOR**: New principles added or existing guidance materially expanded
- **PATCH**: Clarifications, wording improvements, typo fixes

### Compliance Review

- All PRs and code reviews MUST verify compliance with this constitution
- Complexity beyond what is specified MUST be justified in writing
- Runtime development guidance is available in `CLAUDE.md` files

## Final Goal

This constitution governs the Phase III evolution of the Todo application. Every line of code, every design decision, every commit MUST serve the vision of building an AI-powered chatbot that extends the Phase II foundation using Cohere API for LLM reasoning.

We do not build average apps.
We build systems that win hackathons and launch careers.

All agents, subagents, and skills MUST adhere strictly to these principles.
